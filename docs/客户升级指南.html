1. 本次升级概要

Phase 2 在现有平台基础上新增 Storage 子系统,并增强 Edge Functions、项目生命周期管理与安全性。主要变更:

能力说明
Storage(新增)对象存储服务,多租户隔离。新增一个 S3 桶 + 一个 storage 服务 + 数据库 storage schema。
Edge Functions verify_jwt支持部署时设置免 JWT 校验(webhook 场景),一步部署即可。
项目暂停 / 恢复 / 删除暂停后数据面真正停止访问,恢复后还原。
Secrets 覆盖语义同名 secret 覆盖而非堆叠。
函数错误分类代码错误返回 422(而非误导性 404)。
安全加固租户隔离、密钥生命周期、依赖 CVE 修复。
对现有数据零影响:升级不修改任何终端用户的表与数据;数据库变更均为新增(加表 / 加 schema),不影响既有读写。存量 API key、Edge Functions 不失效。

2. 前提条件

执行升级的运维机需具备:

  • docker(可构建 linux/amd64 镜像)
  • node、pnpm、go、deno(各服务构建工具链)
  • aws cli(已配置目标账号凭证)
  • AWS CDK(目标账号已完成 cdk bootstrap)
  • jq(测试脚本依赖)
配置文件不随代码走:config.json 与 certs/ 不纳入版本控制(含部署敏感值)。升级过程不会覆盖它们,但请确认其内容为当前环境的有效配置。

3. 升级前准备

1

备份配置

cp config.json config.json.bak
2

确认 config.json 含 storage 配置段

Phase 2 引入 Storage,config.json 需包含 storage 段(基线版本没有)。若缺失,请参照配置模板 config.production.json 添加:

"storage": {
  "bucket": { "mode": "create" },   // create=新建桶; 或 "existing"+"name"=引用已有桶
  "fileSizeLimitBytes": 52428800,      // 单文件上限(50 MiB)
  "imageTransformationEnabled": false
}

校验:cat config.json | jq '.storage'

3

(建议)消除网关单点中断窗口

若网关服务 kong 的 desiredCount 为 1,升级时其重启会造成数据面短暂中断(数十秒)。建议升级前先将 config.json 中 kong.desiredCount 设为 2 并单独部署一次(选业务低峰),此后网关升级即可零停机。

4. 拉取最新代码

先判断走哪条路径:

  • 运维机已有该项目的 git 仓库且工作区干净 → 走 方式 A(git pull)。
  • 运维机没有仓库,或工作区有未确认的本地改动 → 走 方式 B(git clone)。
  • 习惯把新版本代码复制成新工程目录、沿用原配置更新现有环境 → 走 方式 C。

判断命令:git rev-parse --is-inside-work-tree 与 git status --short。

三种方式的部署结果一致:只要保持栈名、账号/区域、资源物理名不变,A / B / C 都是原地更新同一套环境,后续构建、部署步骤完全相同。区别只在「如何把新代码放到运维机」。

方式 A:git pull(增量更新)

先完成以下前置清理,再执行 pull。否则 pull 可能因本地文件冲突而失败。
# 前置 1:删除本地未跟踪的 lockfile
#   早期版本中该文件未纳入版本控制,运维机本地可能存在一份;
#   新版本已将其纳入 git,若不清理,pull 会报
#   "untracked working tree files would be overwritten by merge"。
rm -f app/function-deploy/pnpm-lock.yaml

# 前置 2:检查本地改动(若 status 非空,先暂存)
git status
git stash        # 仅当存在需保留的本地改动时

# 前置完成后,拉取最新代码
git fetch origin
git pull origin main

# 如之前执行了 stash 且改动仍需要:git stash pop

方式 B:git clone(全新检出)

# 1) 全新克隆到新目录
git clone <repository-url> supabase-app
cd supabase-app
git checkout main

# 2) 迁移不随代码走的本地文件(从原运维目录拷入)
cp <old-dir>/config.json ./config.json
cp -r <old-dir>/certs ./certs

# 3) 确认 config.json 含 storage 段(见第 3 节步骤 2)
cat config.json | jq '.storage'

方式 C:复制新工程目录,沿用原配置更新原有环境

若你习惯将新版本代码复制为一个新的工程目录(而非在原目录 pull),再把原环境的配置拷入、重新部署,这样做会原地更新现有的那一套环境(不会新建第二套)。其本质与方式 B 相同,只是用于「更新现有环境」而非「搭建独立环境」。

# 1) 准备新版本代码目录(克隆或解压新版本)
git clone <repository-url> supabase-app-new
cd supabase-app-new && git checkout main

# 2) 从原环境拷入配置与证书(关键:沿用原配置=更新原环境)
cp <old-dir>/config.json ./config.json
cp -r <old-dir>/certs ./certs
cat config.json | jq '.storage'    # 确认含 storage 段
要更新原有环境,必须保持以下三项与原环境完全一致(沿用原配置即满足):
  • 部署栈名 SupabaseStack(代码内置,勿改)——部署工具按栈名识别目标,栈名一致才会更新原栈而非新建。
  • 同一 AWS 账号与区域(config.json 的 project.accountId / project.region)。
  • 各资源物理名不变:infraStack.cluster.name、loadBalancer.name、studioLoadBalancer.name、workerRds.clusterIdentifier、secrets.prefix、domain.baseDomain。
三项一致 → 后续 cdk deploy SupabaseStack 即对现有环境做增量更新(原地升级),不会产生第二套资源。
反向提醒:上述三项中只要任意一项被改动(尤其是栈名或账号/区域),行为就会变化——可能创建出一套全新的并行环境,或因物理资源名冲突而部署失败。要更新原环境,请勿改动它们。

5. 构建并推送镜像

构建本次升级涉及的服务镜像并推送至 ECR(脚本会自动创建缺失的 ECR 仓库):

./build-and-push.sh storage          # 新增服务
./build-and-push.sh tenant-manager
./build-and-push.sh functions
./build-and-push.sh function-deploy
./build-and-push.sh kong             # 必须:网关路由配置含 Storage 路由
./build-and-push.sh auth
务必重新构建 kong:网关的路由配置(kong.yml.tpl)在 Phase 2 中新增了 Storage 路由。若沿用旧网关镜像,Storage 数据面请求将返回 404 no Route matched。
确认需重建的服务:执行 git diff <基线版本> HEAD --name-only | grep '^app/',凡 app/ 下有代码变更的服务都需重新构建。本次为 storage、tenant-manager、functions、function-deploy、kong、auth。
构建提示:auth 服务(Go)若构建时拉取依赖超时,其 Dockerfile 已配置国内代理;function-deploy 的 lockfile 已纳入版本控制,干净检出即可构建。

6. 部署(CDK)

1

编译并审查变更

cd infra && npm run build
cdk diff SupabaseStack

预期变更:新增 S3 桶、新增 storage 服务、若干任务定义(TaskDefinition)更新。确认变更中不包含数据库集群、S3 桶、缓存等有状态资源的「替换(replace)」——正常升级只更新任务定义,不应替换有状态资源。

版本兼容:请确保 CDK CLI 版本与项目依赖的 aws-cdk-lib 版本兼容。若提示 Cloud assembly schema version mismatch,需升级 CDK CLI 或锁定 aws-cdk-lib 至匹配版本。
2

执行部署

cdk deploy SupabaseStack --require-approval never

该步骤新建 S3 桶与 storage 服务,并更新任务定义。部署过程中关注各服务的滚动状态。

无自动回滚:部署未启用熔断器,异常镜像不会自动回滚。请关注部署状态直至 COMPLETED: 
aws ecs describe-services --cluster <cluster-name> \
  --services storage-api kong-gateway tenant-manager \
  --region <region> \
  --query 'services[*].[serviceName,deployments[0].rolloutState]'

7. 刷新服务镜像(关键步骤)

必做,不可省略:CDK 通过 :latest 标签引用镜像。cdk deploy 仅在任务定义结构发生变化时才会触发服务拉取新镜像。对于代码已更新、但任务定义未变化的服务,cdk deploy 不会使其拉取新镜像,服务将继续运行旧版本代码。

因此,部署完成后,需对所有重新构建过镜像的服务强制刷新一次:

for svc in kong-gateway tenant-manager functions-service \
           function-deploy auth-service storage-api; do
  aws ecs update-service --cluster <cluster-name> \
    --service "$svc" --force-new-deployment --region <region> \
    --query 'service.deployments[0].rolloutState' --output text
done
服务名说明:ECS 服务名与 ECR 仓库名可能不同(如仓库 functions-service / kong-configured 对应服务 functions-service / kong-gateway)。可用 aws ecs list-services --cluster <cluster-name> 查询实际服务名。
数据库迁移(自动):平台数据库与各租户数据库的 schema 变更在对应服务启动时自动执行,均为新增操作,无需手动干预,也无需回滚。

9. 回滚方案

问题回滚方式
镜像异常(服务无法启动)将服务镜像标签回退至上一版本(ECR 保留历史镜像),或回退代码后重新 cdk deploy。
CDK 栈变更检出基线版本代码,执行 cdk deploy 回退(本次升级无破坏性资源变更,可逆)。
数据库迁移无需回滚——均为新增(加表/加 schema),不影响旧代码。
回滚前提:升级前请记录当前各服务镜像标签与代码版本(git rev-parse HEAD),以便必要时回退。

11. 升级机制速查(A/B 路径 · 服务名映射)

升级时如何让改动生效,取决于你改了什么。选错路径是「改了却没生效」最常见的原因。

路径 A:服务代码变更(Docker 镜像)

改动 app/* 下任何服务(Kong 配置、GoTrue、tenant-manager、Studio 等)都需重建镜像并强制 ECS 拉取。cdk deploy 在镜像 tag 不变时不会拉新镜像——任务定义仍指向 :latest,ECS 保持旧任务运行。必须强制刷新:

# 1. 重建并推送(同时推 :latest 与 :<git-sha>)
./build-and-push.sh <service>      # 如 kong、auth、tenant-manager
# 2. 强制 ECS 拉取新 :latest 并替换运行任务
aws ecs update-service --cluster <cluster> --service <service-name> --force-new-deployment --region <region>
# 3. 等待滚动稳定
aws ecs wait services-stable --cluster <cluster> --services <service-name> --region <region>

ECR 仓库名与 ECS 服务名对部分服务不同:

build-and-push.sh 参数ECS 服务名
kongkong-gateway
authauth-service
functionsfunctions-service
storagestorage-api
tenant-manager / studio / function-deploy / postgres-meta同名

路径 B:基础设施变更(CDK)

改动 infra/(VPC、RDS、ECS 任务定义、ALB、IAM、env 等)走 CDK。任务定义变更(新 env、CPU/内存等)会自动滚动服务:

cd infra && npm run build && npx cdk diff SupabaseStack   # 预览
npx cdk deploy SupabaseStack --require-approval never
经验法则:镜像内容变 → 路径 A(force-new-deployment);任务/基础设施定义变 → 路径 B(cdk deploy)。若两者都改了(如新镜像 + 它要读的新 env),先 B 再 A。

Kong 说明(DB-backed 声明式配置)

Kong 以 DB-backed 模式运行,启动时经 kong config db_import 导入 kong.yml.tpl,这是增量 upsert——从不删除配置里已移除的实体。入口脚本在每次启动时跑一个幂等自愈(heal-stale-plugins.lua),清掉旧配置遗留的 service 级鉴权插件。因此对 kong-gateway 直接重建 + force-new-deployment 即可,无需手动清理 DB。

Auth schema 说明(模板克隆 + 存量租户)

新租户库是从缓存的 supabase_template 库克隆而来,并非在空库上跑 DDL;而 schema DDL 用 CREATE TABLE IF NOT EXISTS,对已存在的表是 no-op。因此只改 auth-schema.ts 的 CREATE TABLE 永远无法补列——模板和存量租户库都不会拿到新列,新建租户还会继续克隆旧模板。

tenant-manager 启动时会对模板库以及每个已注册实例上的全部存量租户库执行一组幂等的 ALTER TABLE ... ADD COLUMN IF NOT EXISTS(见 AUTH_SCHEMA_HEAL_STATEMENTS),让全新部署与升级部署都收敛到当前 schema。该自愈幂等(列已存在即跳过)且 fail-open(被锁/暂停的租户库自动跳过,绝不阻断启动)。它纯加列/加约束,不删除、不修改任何现有数据。所以对 tenant-manager 直接重建 + force-new-deployment 即可,无需手动 DROP 模板库或逐库补列。

改表必须同步加补丁:给 auth-schema.ts 的某张表加列后,务必同时往 AUTH_SCHEMA_HEAL_STATEMENTS 加一条对应的 ADD COLUMN IF NOT EXISTS,否则改动只到代码、永远到不了数据库。

11.1 Storage 对象存储(新增)

部署:新增 S3 桶 + storage 服务 + 数据库 storage schema。config.json 的 storage.bucket.mode 决定桶来源:create=CDK 新建并托管;existing+name=引用已有桶(CDK 只授权、不创建/删除)。需重建 storage 与 kong(网关含 Storage 路由)。

# config.json
"storage": { "bucket": { "mode": "create" }, "fileSizeLimitBytes": 52428800, "imageTransformationEnabled": false }
# 构建 + 刷新
./build-and-push.sh storage && ./build-and-push.sh kong
aws ecs update-service --cluster <cluster> --service storage-api --force-new-deployment --region <region>

使用:所有 Storage 请求统一经项目子域走 Kong 网关(Kong 用 key-auth 校验 opaque apikey、注入 X-Project-ID、铸造 5 分钟短期 JWT 给 storage-api;storage-api 据此做多租户隔离)。基址 https://<ref>.<domain>/storage/v1,请求头统一带 apikey: <key>(anon 或 service_role opaque key)。

完整 API 速查(本次新增的对象存储数据面;路径均经源码 app/storage/src/http/routes/ 核对,前缀 /storage/v1。fastify 通配段 * 即对象 path):

11.5 登录增强(Google OAuth / 邮箱改密 / 后台改密)

部署:涉及 4 个服务,按依赖顺序滚动:tenant-manager → auth → kong → function-deploy。tenant-manager 先(建平台库 OAuth provider 表、产出 GoTrue 消费的 external 字段);kong 放行无法携带 apikey 的 OAuth/SAML 回调端点。无新增 env/secret:Google 凭据按租户在运行期录入,client_secret 用既有 ENCRYPTION_KEY 加密入库。

for svc in tenant-manager auth function-deploy; do ./build-and-push.sh $svc; done
./build-and-push.sh kong
for svc in tenant-manager auth-service kong-gateway function-deploy; do
  aws ecs update-service --cluster <cluster> --service $svc --force-new-deployment --region <region>
done

使用:登录增强分两层 —— 管理面(tenant-manager,配 provider,需 admin key)与数据面(GoTrue /auth/v1/*,经 Kong,带项目 apikey)。

① 管理面:per-tenant Google provider 配置(tenant-manager,经 Studio ALB):

方法 + 路径说明
PUT /admin/v1/projects/{ref}/auth/external/googleupsert;body {"enabled","client_id","client_secret","redirect_uri","skip_nonce_check"}。secret 加密入库
GET /admin/v1/projects/{ref}/auth/external/google读取;secret 不回显,仅返回 secret_set:true
DELETE /admin/v1/projects/{ref}/auth/external/google移除该项目的 Google provider
curl -X PUT "https://<studio-alb>/admin/v1/projects/<ref>/auth/external/google" -H "Authorization: Bearer <admin-key>" \
  -H "Content-Type: application/json" \
  -d '{"enabled":true,"client_id":"<gid>.apps.googleusercontent.com","client_secret":"<secret>","redirect_uri":"https://<ref>.<domain>/auth/v1/callback"}'

② 数据面:GoTrue 认证端点(基址 https://<ref>.<domain>/auth/v1,带 apikey: <anon-key>;/callback 等回调端点由 Kong 放行、无需 apikey。路径经源码 app/supabase-auth/internal/api/api.go 核对):

需求方法 + 路径body / 说明
5a 发起 Google 登录GET /authorize?provider=google302 重定向到 Google,带本租户 client_id
5a OAuth 回调GET /callback 与 POST /callbackGoogle 重定向回此(免 apikey),换 token 建 session
5a 读取 provider 状态GET /settings返回 external.google 是否启用
5b 邮箱发重置码POST /recoverbody {"email":"..."}(无 type 字段)→ 发重置邮件
5b 校验并改密POST /verify(亦有 GET /verify)body {"type":"recovery","email":"...","token":"<code>"}(或 token_hash)
5b OTP(可选)POST /otpbody {"email":"..."} 发一次性码
5c 后台改用户密码经 Studio 后台 PATCH /api/platform/auth/{ref}/users/{id}由 Studio 内部用 service 凭证调 GoTrue;不要客户直接打 GoTrue admin(见下方注意)
# 5a 发起 Google 登录(浏览器跳转或 supabase-js signInWithOAuth)
GET https://<ref>.<domain>/auth/v1/authorize?provider=google      # 带 apikey

# 5b 邮箱发重置码(recover body 仅含 email,无 type)
curl -X POST "https://<ref>.<domain>/auth/v1/recover" -H "apikey: <anon-key>" \
  -H "Content-Type: application/json" -d '{"email":"user@example.com"}'
# 用户收到验证码后,verify 带 type=recovery 完成改密
curl -X POST "https://<ref>.<domain>/auth/v1/verify"  -H "apikey: <anon-key>" \
  -H "Content-Type: application/json" -d '{"type":"recovery","email":"user@example.com","token":"<code>"}'

# 5c 后台修改某用户密码 —— 经 Studio 后台 API(Studio 内部持 service 凭证)
curl -X PATCH "https://<studio-alb>/api/platform/auth/<ref>/users/<user_id>" \
  -H "Content-Type: application/json" -d '{"password":"NewPassw0rd!"}'
5c 实测要点(经真实环境验证):GoTrue 的 /auth/v1/admin/* 端点要求 service_role/supabase_admin 角色的 JWT;而本平台 Kong 的 /auth/v1 路径只透传 opaque key、不铸造 JWT。因此客户直接用 sb_secret_ opaque key 打 /auth/v1/admin/users/{id} 会返回 403 bad_jwt(实测)。后台改密应经 Studio 后台(由 Studio 用内部 SUPABASE_SERVICE_KEY 调 auth.admin.updateUserById())。
supabase-js 等价:signInWithOAuth({provider:'google'})(5a)、resetPasswordForEmail(email)+verifyOtp({type:'recovery',...})(5b)。5c 在持有 service_role JWT 的服务端可用 auth.admin.updateUserById(id,{password})。
管理面 PUT provider 的 body:enabled 必填;当 enabled=true 时 client_id / client_secret / redirect_uri 三者必填;skip_nonce_check 可选(默认 false)。GET 读取时不返回 client_secret,仅返回 secret_set: true/false。

需在 Google Cloud Console 把 https://<ref>.<domain>/auth/v1/callback 加入授权回调 URL。

测试:PROJECT_REF=<ref> ./RUN_TESTS.sh oauth —— O0 取 anon key、O1 provider CRUD(加密+掩码)、O2 GoTrue /settings 反映租户 google、O3 Kong 放行 OAuth/SAML 端点、O4 受保护端点仍 key-auth、O5 /authorize 重定向到 Google 带租户 client_id(硬断言)。

flow_state 缺列已由启动自愈解决:tenant-manager 启动时的 auth-schema 自愈(AUTH_SCHEMA_HEAL_STATEMENTS,见第 11 节)会对模板库及每个存量租户库执行 ALTER TABLE … ADD COLUMN IF NOT EXISTS,补齐 auth.flow_state 的 OAuth 上下文列。因此升级后 /authorize?provider=google 正常返回 302(带本租户 client_id),O5 已作为硬断言通过——早期版本中该项曾因缺列返回 500 而临时标 xfail,现已修复。
O2/O5 偶发失败=GoTrue 缓存传导延迟(非缺陷):GoTrue 对租户 provider 配置有两层缓存(Manager TTL 5 分钟 + 连接池冻结),且无主动失效通路。通过管理面刚 PUT 完 provider 立即跑 O2(/settings)/O5(/authorize) 可能读到旧值而失败;等缓存自然淘汰(空闲约 10 分钟 / LRU)后即恢复。若测试时遇到,稍候重跑或在配置与验证间留出传导窗口即可,功能本身正常。
